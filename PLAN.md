# Wolfpack: план реализации языка для Claude Code

Oct 7, 2026

## 1. Суть проекта и цели

Wolfpack — статически типизированный язык, компилятор которого транслирует файлы `.wolf` в читаемый код на TypeScript, Go и Rust. Команда компилятора — wolf, манифест проекта — wolfpack.toml.

У языка две отличительные идеи:

- **Жёсткий каркас файла.** Каждый файл состоит из секций в фиксированном порядке. Нарушение порядка — ошибка компиляции, а не замечание линтера.
- **Единая раскладка проекта.** Точка входа, папки и манифест одинаковы для любого проекта и любой цели трансляции.

Цели автора: прокачать навыки в системном программировании и получить сильный проект для портфолио. Отсюда главный принцип: маленький, но законченный язык с хорошими сообщениями об ошибках, тестами и документацией важнее широкого, но недоделанного.

Ядро языка — это пересечение возможностей трёх целей. Всё, что есть только в одной цели, доступно через `extern` (раздел 7).

## 2. Принятые решения

Эти решения зафиксированы. Менять их можно только через правку спецификации с согласия автора.

| Вопрос | Решение |
| --- | --- |
| Язык компилятора | Rust |
| Цели трансляции | TypeScript, Go, Rust. Порядок реализации бэкендов: TS, затем Go, затем Rust |
| Типизация | Статическая, строгая. Вывод типов только для локальных переменных |
| Память | Владение без лайфтаймов (раздел 4) |
| Ошибки | `Result<T, E>` и оператор `?`. Исключений нет |
| Отсутствие значения | `Option<T>`. `null` нет |
| ООП | `struct` + `interface` + `impl`. Наследования нет |
| Секции файла | Порядок фиксирован, дублирование запрещено, пустые секции не пишутся |
| Сгенерированный код | Читаемый и идиоматичный для каждой цели |
| Байткод | Отдельный бэкенд со своей виртуальной машиной, после трёх основных целей |
| Библиотеки | Своя маленькая `std` плюс `extern` для библиотек целевого языка |
| Виды проектов в v1 | Консольная программа (`cli`) и библиотека (`lib`) |
| Асинхронность | Не входит в v1 |

## 3. Обзор языка

Язык намеренно маленький: в нём только то, что одинаково хорошо ложится на все три цели.

**Встроенные типы:** `Int`, `Float`, `Bool`, `String` (UTF-8, неизменяемая), `Void`, `List<T>`, `Map<K, V>`, `Option<T>`, `Result<T, E>`.

**Пользовательские типы:**

- `struct` — запись с именованными полями.
- `enum` — тип-сумма, варианты могут нести данные.
- `interface` — набор сигнатур методов.
- Дженерики с ограничениями по интерфейсам: `fn max<T: Comparable>(a: T, b: T) -> T`.

**Переменные:** `let` — неизменяемая, `var` — изменяемая. Тип локальной переменной выводится, типы параметров и результата функции пишутся всегда.

**Управление:** `if`/`else` и `match` — выражения. `match` обязан покрывать все варианты. Циклы `while` и `for x in collection`. Оператор `?` пробрасывает ошибку из `Result`. `panic("...")` — для неисправимых ситуаций.

**Чего в языке нет:** наследования, `null`, исключений, неявных преобразований типов, перегрузки функций и операторов, глобального изменяемого состояния, макросов, рефлексии.

**Видимость:** всё приватно для модуля, `pub` открывает наружу.

**Именование:** в Wolfpack `snake_case` для функций и переменных, `PascalCase` для типов. Бэкенды переводят имена в стиль цели: `camelCase` в TS, `PascalCase` для экспортируемых имён в Go.

```
fn find_user(users: List<User>, id: Int) -> Option<User> {
    for u in users {
        if u.id == id {
            return Some(u.copy())
        }
    }
    None
}

fn load(path: String) -> Result<Config, Error> {
    let text = fs.read_text(path)?
    parse_config(text)
}
```

## 4. Модель памяти: владение без лайфтаймов

В языке есть владение и заимствование, но ссылки нельзя хранить и возвращать, поэтому лайфтаймы не нужны. Это компромисс между «всё копируется» и полной моделью Rust: код на Rust получается идиоматичным, а язык остаётся простым. Подход известен как mutable value semantics (языки Hylo и Swift).

**Правила:**

1. У каждого значения один владелец.
2. Присваивание и передача составного значения перемещают его. Использование после перемещения — ошибка компиляции.
3. Примитивы (`Int`, `Float`, `Bool`) копируются неявно. Всё остальное копируется только явно: `x.copy()`.
4. У параметра функции один из трёх режимов:
   - без пометки — чтение, значение одалживается;
   - `mut` — изменение на месте, эксклюзивный доступ;
   - `own` — функция забирает значение себе.
5. В месте вызова режим виден: `sort(mut items)`, `save(own user)`.
6. Ссылка не может быть полем структуры и не может быть результатом функции.
7. Одну переменную нельзя передать в один вызов дважды, если хотя бы один раз она передаётся как `mut`.

```
fn rename(mut u: User, name: String) {
    u.name = name.copy()
}

fn archive(own u: User) -> ArchivedUser { ... }

var user = User { id: 1, name: "Ann" }
rename(mut user, "Anna")
let old = archive(own user)
print(user.name)   // ошибка: user перемещён в archive
```

**Как это ложится на цели:**

| Режим | Rust | Go | TypeScript |
| --- | --- | --- | --- |
| чтение | `&T` | значение или `*T` для крупных структур | ссылка на объект |
| `mut` | `&mut T` | `*T` | ссылка на объект |
| `own` | `T` | значение | ссылка на объект |
| `.copy()` | `.clone()` | сгенерированная функция копирования | сгенерированная функция копирования |

В Go и TS копии не нужны: проверки компилятора Wolfpack гарантируют, что на изменяемое значение нет второй ссылки.

**Ограничения, о которых надо знать заранее:**

- Рекурсивные типы (деревья) разрешены: бэкенд Rust сам оборачивает рекурсивные поля в `Box`.
- Графы с циклами описываются через индексы в `List`, а не через ссылки.
- Разделяемое владение (`Shared<T>`, аналог `Rc`) не входит в v1.
- Замыкания в v1 захватывают значения только копией или перемещением.

## 5. Каркас файла

Файл начинается строкой `module` и дальше состоит только из секций в порядке из таблицы. Вне секций допустимы только комментарии.

| № | Секция | Что в ней |
| --- | --- | --- |
| 0 | `module` | Одна строка с именем модуля. Обязательна. Имя совпадает с путём файла |
| 1 | `imports` | Импорты модулей проекта и `std` |
| 2 | `extern` | Объявления функций и типов из библиотек целевого языка, блок на каждую цель |
| 3 | `config` | Константы и настройки модуля. Только неизменяемые значения |
| 4 | `types` | `struct`, `enum`, псевдонимы типов |
| 5 | `interfaces` | Интерфейсы |
| 6 | `impl` | Методы типов и реализации интерфейсов |
| 7 | `functions` | Свободные функции |
| 8 | `tests` | Тесты модуля |

**Правила:**

- Порядок секций фиксирован. Нарушение — ошибка компиляции с кодом и подсказкой, куда секцию перенести.
- Секция встречается в файле не больше одного раза.
- Пустая секция не пишется. Пустой блок `types { }` — ошибка.
- Объявление не в своей секции — ошибка: `struct` внутри `functions` не скомпилируется.
- Порядок объявлений внутри секции свободный.

```
module users.storage

imports {
    std.fs
    users.model.{User}
}

extern {
    go {
        fn sha256(input: String) -> String from "crypto/sha256"
    }
}

config {
    max_users: Int = 100
    data_file: String = "users.db"
}

types {
    pub struct FileStorage {
        path: String
        count: Int
    }

    pub enum StorageError {
        Full
        Io(String)
    }
}

interfaces {
    pub interface Storage {
        fn save(mut self, u: User) -> Result<Void, StorageError>
    }
}

impl {
    FileStorage: Storage {
        fn save(mut self, u: User) -> Result<Void, StorageError> {
            if self.count >= max_users {
                return Err(StorageError.Full)
            }
            self.count = self.count + 1
            Ok(())
        }
    }
}

functions {
    pub fn open(path: String) -> FileStorage {
        FileStorage { path: path.copy(), count: 0 }
    }
}

tests {
    test "new storage is empty" {
        let s = open("tmp.db")
        assert(s.count == 0)
    }
}
```

Синтаксис в примере — отправная точка для спецификации, а не окончательный вариант.

## 6. Раскладка проекта и манифест

Раскладка одна для всех проектов, компилятор отказывается собирать проект с другой структурой.

```
my-app/
  wolfpack.toml        манифест
  src/
    main.wolf          точка входа для kind = "cli" (содержит fn main)
    lib.wolf           публичный API для kind = "lib"
    users/
      model.wolf       модуль users.model
      storage.wolf     модуль users.storage
  tests/               интеграционные тесты
  examples/            примеры использования
  out/
    ts/  go/  rust/    сгенерированные проекты, в git не попадают
```

**Правила модулей:**

- Один файл — один модуль. Путь `src/users/storage.wolf` даёт модуль `users.storage`.
- Файлы-индексы для папок не нужны и запрещены.
- Точка входа всегда `src/main.wolf` или `src/lib.wolf`, в зависимости от `kind`. Других вариантов нет.
- Циклические импорты запрещены.

**Манифест:**

```toml
[package]
name = "my-app"
version = "0.1.0"
kind = "cli"              # cli | lib

[targets]
default = "ts"
enabled = ["ts", "go", "rust"]

[extern.go.dependencies]
"github.com/some/lib" = "v1.2.0"

[extern.ts.dependencies]
"some-lib" = "^2.0.0"
```

**Что получается на выходе.** Для каждой цели компилятор создаёт полноценный проект, готовый к запуску штатными инструментами:

| Цель | Содержимое `out/<цель>/` |
| --- | --- |
| TypeScript | `package.json`, `tsconfig.json` в strict-режиме, `src/**/*.ts` |
| Go | `go.mod`, пакеты по папкам, `main.go` |
| Rust | `Cargo.toml`, `src/main.rs` или `src/lib.rs`, модули по файлам |

Структура папок в `out` повторяет структуру `src`, чтобы по сгенерированному файлу легко находился исходный.

## 7. Библиотеки: std и extern

Есть два способа пользоваться библиотеками, и автор выбирает нужный для каждого модуля.

**Своя `std`.** Маленькая, одинаково работает на всех целях. Состав для v1:

| Модуль | Что даёт |
| --- | --- |
| `std.io` | `print`, `read_line`, аргументы командной строки |
| `std.string` | длина, срезы, поиск, разбиение, преобразование в число и обратно |
| `std.list`, `std.map` | базовые операции над коллекциями |
| `std.math` | `min`, `max`, `abs`, `pow`, `sqrt` |
| `std.fs` | чтение и запись файла целиком |
| `std.process` | код выхода, переменные окружения |

Функции `std` объявлены в `.wolf`-файлах с пометкой `intrinsic`. Реализацию для каждой цели даёт соответствующий бэкенд.

**`extern`.** Объявляет функции и типы из библиотек целевого языка:

- Модуль с `extern` только для Go становится привязанным к цели. Сборка под TS или Rust даёт понятную ошибку с именем модуля и секции.
- Если одна и та же сигнатура объявлена во всех трёх блоках (`ts`, `go`, `rust`), модуль остаётся переносимым.
- Зависимости целевого языка указываются в манифесте в `[extern.<цель>.dependencies]` и попадают в `package.json`, `go.mod` или `Cargo.toml`.
- Через границу `extern` проходят только примитивы, `String`, `List`, `Option` и `Result`. Правила преобразования описываются в спецификации для каждой цели.

Так достигается требование «поддерживать всё, что умеют целевые языки»: ядро языка общее, а всё специфичное приходит через `extern`.

## 8. Отображение на целевые языки

Каждая конструкция Wolfpack переводится в самую естественную конструкцию цели. Таблица — исходная точка, точные правила фиксируются в спецификации бэкендов.

| Wolfpack | TypeScript | Go | Rust |
| --- | --- | --- | --- |
| `Int` | `number` | `int64` | `i64` |
| `Float` | `number` | `float64` | `f64` |
| `String` | `string` | `string` | `String` и `&str` |
| `List<T>` | `T[]` | `[]T` | `Vec<T>` |
| `Map<K, V>` | `Map<K, V>` | `map[K]V` | `HashMap<K, V>` |
| `Option<T>` | `T \| undefined` | `*T` | `Option<T>` |
| `Result<T, E>` | объединение `{ ok: true, value }` и `{ ok: false, error }` | `(T, error)` | `Result<T, E>` |
| `struct` | `interface` и функция-конструктор | `struct` | `struct` |
| `enum` с данными | размеченное объединение | закрытый интерфейс и структура на вариант | `enum` |
| `interface` | `interface` | `interface` | `trait` |
| `impl` | функции модуля или методы | методы с получателем | `impl` |
| дженерики | дженерики | дженерики | дженерики с ограничениями по трейтам |
| `match` | `switch` по тегу с проверкой полноты | `switch` по типу | `match` |
| оператор `?` | ранний `return` | `if err != nil { return ... }` | `?` |
| `panic` | `throw new Error` | `panic` | `panic!` |
| `tests` | `node:test` | пакет `testing` | `#[test]` |

Тип `Int` в TypeScript — известная проблема: `number` точно хранит целые только до 2^53. Решение вынесено в открытые вопросы (раздел 14).

**Требования к сгенерированному коду:**

- Проходит штатную проверку цели без ошибок: `tsc --strict`, `go vet`, `cargo check`.
- Отформатирован так, как это сделал бы `prettier`, `gofmt` или `rustfmt`.
- Документирующие комментарии из исходника переносятся в результат.
- Вывод детерминирован: одинаковый вход всегда даёт побайтно одинаковый результат.
- В начале каждого файла комментарий с путём к исходному `.wolf`.

## 9. Архитектура компилятора

Компилятор — Cargo workspace из небольших крейтов, по одному на этап. Бэкенды работают только с промежуточным представлением и не видят синтаксическое дерево.

**Этапы компиляции:**

1. Чтение манифеста и поиск файлов проекта.
2. Лексер: текст в токены.
3. Парсер: токены в AST. Здесь же проверяется каркас файла.
4. Разрешение имён: модули, импорты, видимость.
5. Проверка типов: вывод локальных типов, дженерики, полнота `match`.
6. Проверка владения: перемещения и эксклюзивность `mut`.
7. Понижение в IR: типизированное дерево без синтаксического сахара.
8. Бэкенд: IR в дерево целевого языка.
9. Печать: дерево целевого языка в текст и файлы проекта.

**Крейты:**

| Крейт | Ответственность |
| --- | --- |
| `wolf_span` | Исходные файлы, позиции, диапазоны |
| `wolf_diag` | Диагностики: код, сообщение, диапазон, подсказка, вывод в терминал |
| `wolf_lexer` | Лексер, написан вручную |
| `wolf_ast` | Типы синтаксического дерева |
| `wolf_parser` | Рекурсивный спуск, парсер Пратта для выражений, восстановление после ошибок |
| `wolf_resolve` | Модули, импорты, таблицы имён |
| `wolf_types` | Проверка типов |
| `wolf_own` | Проверка владения |
| `wolf_ir` | Промежуточное представление и понижение из AST |
| `wolf_backend_ts`, `_go`, `_rust` | Генерация кода, по крейту на цель |
| `wolf_std` | Объявления стандартной библиотеки |
| `wolf_project` | Манифест, раскладка проекта |
| `wolf_cli` | Исполняемый файл `wolf` |

Позже добавятся `wolf_fmt`, `wolf_vm` и `wolf_lsp`.

**Принципы:**

- Лексер и парсер пишутся вручную, без генераторов. Так лучше сообщения об ошибках, и это сильнее смотрится в портфолио.
- Компилятор не останавливается на первой ошибке: собирает все, какие может, и показывает разом.
- У каждой диагностики есть уникальный код (`E0101`), диапазон в исходнике и, где возможно, подсказка с исправлением.
- Компилятор никогда не паникует на пользовательском вводе. Любой некорректный файл даёт диагностику.
- Каждый бэкенд сначала строит дерево целевого языка, потом печатает его. Склейка строк напрямую из IR запрещена.

**Внешние зависимости:** `clap` для CLI, `serde` и `toml` для манифеста, `codespan-reporting` или `ariadne` для вывода диагностик, `insta` для снапшот-тестов. Остальное пишется самостоятельно.

## 10. CLI

Весь инструментарий — один исполняемый файл `wolf`.

| Команда | Что делает |
| --- | --- |
| `wolf new <имя> --kind cli\|lib` | Создаёт проект со стандартной раскладкой |
| `wolf check` | Проверяет проект без генерации кода |
| `wolf build --target ts\|go\|rust\|all` | Генерирует проект в `out/<цель>/` |
| `wolf run [--target <цель>]` | Собирает и запускает через инструменты цели |
| `wolf test [--target <цель>]` | Запускает секции `tests` и папку `tests/` |
| `wolf fmt` | Форматирует исходники |
| `wolf explain <код>` | Показывает развёрнутое описание ошибки с примером |

После появления виртуальной машины добавится `wolf run --vm`: запуск без установленных Node, Go или Rust.

## 11. Этапы реализации

Этапы идут строго по порядку. Следующий начинается только после того, как выполнен критерий готовности предыдущего и автор его принял.

| Этап | Что делаем | Готово, когда |
| --- | --- | --- |
| M0. Спецификация | `docs/spec/`: грамматика в EBNF, правила секций, система типов, правила владения, отображение на цели. 10 программ-примеров в `examples/` | Автор прочитал и утвердил спецификацию. Кода компилятора ещё нет |
| M1. Основа | Workspace, `wolf_span`, `wolf_diag`, лексер, заготовка CLI, CI | `wolf check` разбирает файл на токены и показывает лексические ошибки с подсветкой места |

## 12. Тестирование

Тесты пишутся вместе с кодом каждого этапа, этап без тестов не считается готовым.

| Вид тестов | Что проверяет | Где лежит |
| --- | --- | --- |
| Модульные | Отдельные функции крейта | рядом с кодом, `#[cfg(test)]` |
| Снапшоты (`insta`) | Токены, AST, IR и сгенерированный код для фиксированных входов | `tests/snapshots/` в каждом крейте |
| UI-тесты диагностик | Для файла с ошибкой ожидается точный текст сообщения | `tests/ui/*.wolf` и `*.stderr` рядом |
| Сквозные | Пример компилируется в цель, запускается, вывод сравнивается с эталоном | `examples/*/expected.txt` |
| Дифференциальные | Один пример даёт одинаковый вывод во всех целях и в VM | общий прогон в CI |
| Фаззинг (`cargo-fuzz`) | Лексер и парсер не паникуют на случайном вводе | `fuzz/` |

**CI на GitHub Actions:** `cargo fmt --check`, `cargo clippy -- -D warnings`, `cargo test`, затем сквозные тесты с установленными Node, Go и Rust.

## 13. Правила работы для Claude Code

Этот раздел стоит перенести в `CLAUDE.md` в корне репозитория.

**Порядок работы:**

1. Начни с этапа M0. Не пиши код компилятора, пока автор не утвердил спецификацию.
2. Работай над одним этапом за раз. Не забегай в следующие.
3. В конце этапа покажи результат: что работает, какие тесты добавлены, что отложено.
4. После каждого этапа коротко объясни автору, как устроено сделанное и почему так. Одна из целей проекта — обучение.

**Спецификация — источник истины:**

- Любое изменение языка начинается с правки `docs/spec/` отдельным коммитом и требует согласия автора.
- Не добавляй в язык возможности по своей инициативе. Идеи записывай в `docs/ideas.md`.
- Если спецификация неполна или противоречива, остановись и задай вопрос, а не выбирай молча.
- Решения о внутреннем устройстве компилятора принимай сам, решения о поведении языка — только с автором.

**Качество кода:**

- Без `unsafe`. Без `unwrap`, `expect` и `panic!` на путях, зависящих от пользовательского ввода.
- Каждая диагностика имеет код, диапазон и тест. Коды перечислены в одном файле и не переиспользуются.
- Бэкенды читают только IR.
- Перед каждым коммитом: `cargo fmt`, `cargo clippy -- -D warnings`, `cargo test`.
- Коммиты маленькие, в формате Conventional Commits.
- Публичные типы и функции крейтов документированы.

**Документы в репозитории:**

- `docs/spec/` — спецификация языка.
- `docs/decisions/` — короткие записи о принятых решениях и причинах.
- `docs/ideas.md` — отложенные идеи.
- `CHANGELOG.md` — обновляется в конце каждого этапа.

## 14. Открытые вопросы и границы v1

Эти вопросы надо закрыть на этапе M0, до начала кода. К каждому дан вариант по умолчанию.

| № | Вопрос | Вариант по умолчанию |
| --- | --- | --- |
| 1 | Имя wolfpack на crates.io занято другим проектом | Публиковать как `wolfpack-lang`, исполняемый файл называть `wolf` |
| 2 | Размер `Int`: в TS `number` точен только до 2^53 | `Int` 64-битный в Go и Rust, в TS `number` с проверкой переполнения за 2^53 в отладочной сборке. Альтернатива: `Int` 32-битный везде и отдельный `Int64` |
| 3 | Байткод: свой формат или WebAssembly | Свой стековый байткод и VM. Проще в реализации и нагляднее для портфолио |
| 4 | Секция `config`: только константы или значения можно переопределять | Константы с возможностью переопределить из `[config]` в манифесте при сборке |
| 5 | Методы: отдельная секция `impl` или внутри `struct` | Отдельная секция `impl`, как в разделе 5 |
| 6 | Что могут захватывать замыкания | Только копии и перемещённые значения |
| 7 | `Option<T>` в Go: указатель или пара `(T, bool)` | Указатель для структур, пара для примитивов |
| 8 | Порядок объявлений внутри секции | Свободный. Форматтер его не меняет |
| 9 | Целочисленное переполнение | Паника во всех целях |

**Не входит в v1:**

- асинхронность и многопоточность;
- наследование, макросы, рефлексия, перегрузка операторов;
- разделяемое владение `Shared<T>`;
- реестр пакетов и зависимости между проектами Wolfpack;
- виды проектов для веба и GUI;
- LSP и плагины для редакторов;
- бэкенд LLVM.
