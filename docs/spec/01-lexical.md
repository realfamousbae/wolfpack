# Chapter 1: Lexical structure

Status: **APPROVED** (author, 2026-10-07). Every **[PROPOSAL]** item in this chapter is accepted.

This chapter defines how source text becomes a sequence of tokens. Grammar, operator precedence and
the meaning of tokens belong to chapter 3. Diagnostic code ranges belong to chapter 9; the codes
named here are proposals for the lexical range.

## 1. Source text

1. A source file is a `.wolf` file encoded in **UTF-8**. A file that is not valid UTF-8 is rejected
   with diagnostic E0101 pointing at the first invalid byte. **[PROPOSAL]**
2. A UTF-8 byte order mark at the very start of the file is ignored. **[PROPOSAL]**
3. Line terminators are `LF` and `CR LF`. Both count as one newline. A `CR` that is not followed by
   `LF` is an error (E0110). **[PROPOSAL]**
4. Whitespace is space (U+0020), horizontal tab (U+0009) and newline. Any other whitespace or
   control character outside a comment is an error (E0102). **[PROPOSAL]**
5. Non-ASCII characters may appear only inside comments and string literals. **[PROPOSAL]**
6. Positions in diagnostics are reported as line and column, where the column counts Unicode scalar
   values (consistent with G1). Internally the compiler stores byte offsets. **[PROPOSAL]**

## 2. Comments

Comments follow the Rust rules (author, D1.6).

| Form | Kind | Documents |
| --- | --- | --- |
| `// ...` | line comment | nothing |
| `/* ... */` | block comment, **nests**: `/* a /* b */ c */` is one comment | nothing |
| `/// ...` | outer doc comment (line) | the declaration that follows |
| `/** ... */` | outer doc comment (block) | the declaration that follows |
| `//! ...` | inner doc comment (line) | the enclosing item; at the top of a file, the module |
| `/*! ... */` | inner doc comment (block) | the enclosing item; at the top of a file, the module |

1. `//` comes from `PLAN.md` (section 4); the rest is the Rust set.
2. As in Rust, `////...` (four or more slashes), `/**/` and `/***...` are ordinary comments, not doc
   comments.
3. A block comment that is not closed before the end of the file is an error (E0112). Inside a
   block comment, `"` and other characters have no meaning; only `/*` and `*/` are counted.
4. Doc comments are tokens, not whitespace: the compiler keeps them because they are carried into the
   generated code **[PLAN]** (section 8). Where outer and inner doc comments may appear is defined
   in chapter 3.
5. Ordinary comments are kept as trivia attached to tokens so that `wolf fmt` (M12) can preserve
   them. They have no meaning for the language.
6. For statement termination (section 7), a block comment that contains a newline counts as a
   newline; one without a newline counts as a space.

```
/// Returns the user with the given id.
fn find_user(users: List<User>, id: Int) -> Option<User> {
    // linear search is fine for v1
    ...
}
```

## 3. Identifiers

1. An identifier matches `[A-Za-z_][A-Za-z0-9_]*`, ASCII only. **[PROPOSAL]**
   Reason: backends rewrite names (`snake_case` to `camelCase` in TS, exported names to
   `PascalCase` in Go), and that is only predictable for ASCII.
2. The single character `_` is not an identifier. It is the wildcard token (used in patterns, chapter
   3).
3. Identifiers starting with `__` are reserved for names generated by the compiler. **[PROPOSAL]**
4. Naming style **[PLAN]** (section 3), enforced as a compile error **[PROPOSAL]** (see D1.5):

   | Kind | Style | Pattern |
   | --- | --- | --- |
   | functions, methods, variables, parameters, fields, `config` constants, module path segments | `snake_case` | `[a-z][a-z0-9]*(_[a-z0-9]+)*` |
   | types, enum variants, interfaces, type parameters | `PascalCase` | `[A-Z][A-Za-z0-9]*` |

   The strict `snake_case` pattern forbids `__`, a leading or a trailing `_`. That way two different
   Wolfpack names can never collapse into the same `camelCase` name.
   The lexer itself does not check style. The check runs during name resolution because it depends
   on what kind of name it is.
5. A name that is a keyword in a target language (`type`, `func`, `default`, `chan`, ...) is a valid
   Wolfpack identifier. Backends rename it. The rules are in chapter 8.

## 4. Keywords

Keywords are split into **reserved** words, which can never be used as identifiers, and
**contextual** words, which have special meaning only in a specific position and are ordinary
identifiers everywhere else. **[PROPOSAL]** (see D1.4)

Reserved:

```
module   extern   impl     fn       pub      let      var      type
struct   enum     interface
if       else     match    while    for      in       return   break    continue
mut      own      self     Self     true     false
async    await
```

`async` and `await` are reserved for a future version and have no meaning in v1. They are reserved
now so that adding them later does not break existing code.

Contextual:

| Word | Special only when |
| --- | --- |
| `imports`, `config`, `types`, `interfaces`, `functions`, `tests` | at the top level of a file, as a section header followed by `{` |
| `ts`, `go`, `rust` | as a block header directly inside `extern { }` |
| `from` | after a signature inside an `extern` block |
| `intrinsic` | as a modifier of a declaration in a `std` module (chapter 7) |
| `test` | at the start of a declaration inside `tests { }` |

So `let config = load()` and `let types = List.new()` are valid.

`Some`, `None`, `Ok` and `Err` are not keywords. They are the variant names of the built-in enums
`Option` and `Result` (chapter 4). `print`, `panic` and `assert` are ordinary functions.

## 5. Literals

### 5.1 Integer literals

```
int_lit   = dec_lit | hex_lit | oct_lit | bin_lit
dec_lit   = "0" | [1-9] ( "_"? [0-9] )*
hex_lit   = "0x" [0-9a-fA-F] ( "_"? [0-9a-fA-F] )*
oct_lit   = "0o" [0-7] ( "_"? [0-7] )*
bin_lit   = "0b" [01] ( "_"? [01] )*
```

1. Integer literals have no sign. `-5` is the unary minus applied to `5`.
2. `_` may appear only between two digits: `1_000_000` is valid, while `1_`, `_1`, `1__0` and
   `0x_1` are not (E0107).
3. A leading zero is not allowed (`007`, E0107). Octal is written `0o7`; this rules out the C
   confusion where `010` means 8. Prefixes are lower case only (`0X1` is E0107).
4. The value of a literal must not exceed 2^63 (E0106). The value 2^63 (`9223372036854775808`) is
   valid only as the direct operand of a unary minus, so `-9223372036854775808` is the minimum
   `Int`. That check happens after parsing (chapter 4).
5. **Reserved for the future: type suffixes.** A number literal immediately followed by a letter,
   digit or `_` that is not part of the literal is an error (E0107): `5i32`, `1.0f`, `0b102`,
   `0xfg`. This keeps the door open for suffixes such as `5i32` if sized integer types are added
   later, without changing the meaning of any valid program.

### 5.2 Float literals

```
float_lit = dec_digits "." dec_digits exponent?
          | dec_digits exponent
exponent  = ( "e" | "E" ) ( "+" | "-" )? dec_digits
dec_digits = [0-9] ( "_"? [0-9] )*
```

1. Digits are required on **both** sides of `.`. `1.` and `.5` are not floats (E0107). This keeps
   `1.copy()` and other method calls on literals unambiguous.
2. An exponent without a dot is allowed and makes a float, as in Rust: `1e10` and `2E-3` are
   `Float`. An exponent without digits (`1.0e`, `1e+`) is an error (E0107).
3. Hex, octal and binary floats do not exist.
4. A literal that rounds to infinity is an error (E0108). There are no `NaN` or `inf` literals.

### 5.3 String literals

1. A string literal is enclosed in `"`. It may not contain a raw newline (E0103: an unterminated
   string at the end of the line). **[PROPOSAL]**
2. Escape sequences:

   | Escape | Meaning |
   | --- | --- |
   | `\n` | line feed |
   | `\r` | carriage return |
   | `\t` | tab |
   | `\0` | U+0000 |
   | `\xHH` | ASCII character, exactly 2 hex digits, at most `7F` |
   | `\\` | backslash |
   | `\"` | double quote |
   | `\u{H...}` | Unicode scalar value, 1 to 6 hex digits |

   Any other escape is an error (E0104). A `\u{...}` that is empty, too long, a surrogate
   (U+D800 to U+DFFF) or above U+10FFFF is an error (E0105), as is a `\x` escape above `7F`.
3. Control characters other than tab must be escaped (E0109).
4. There is no string interpolation, no raw string and no multiline string in v1, and no character
   literal, because there is no `Char` type in `PLAN.md`. These are recorded in `docs/ideas.md`.
5. **Reserved for the future: literal prefixes.** An identifier immediately followed by `"` is an
   error (E0113): `f"..."`, `r"..."`, `b"..."`. This is the Rust 2021 rule. It means a future
   interpolated string can be `f"{name}"` while `{` in a plain string stays an ordinary character
   forever, and raw strings can be `r"..."`, without breaking any valid program.
6. **Reserved for the future: `'`.** The character `'` is not used in v1 and is an error (E0102,
   with a hint that strings use `"`). It stays free for a possible `Char` literal.
7. Forbidding raw newlines in strings is also deliberate: allowing them later is a compatible
   change, while forbidding them later would not be.

### 5.4 Other values

- `true` and `false` are keywords.
- The `Void` value `()` is two tokens, `(` and `)`. **[PLAN]** (`Ok(())` in section 5)
- There is no `null` **[PLAN]**.

## 6. Operators and punctuation

```
(   )   [   ]   {   }   ,   .   ..  :   ?   _
=   ->  =>
+   -   *   /   %
==  !=  <   <=  >   >=
&&  ||  !
&   |   ^   ~   <<  >>
+=  -=  *=  /=  %=  &=  |=  ^=  <<=  >>=
```

1. The lexer always takes the longest match: `->` is one token, `- >` is two.
2. Usage that comes from `PLAN.md`: `.` for module paths, fields, methods and variants
   (`StorageError.Full`, there is no `::`); `.{` in imports (`users.model.{User}`) is the two tokens
   `.` and `{`; postfix `?`; `->` in signatures.
3. Bitwise and shift operators `&`, `|`, `^`, `~`, `<<`, `>>` exist (author, D1.7). Nested generic
   types such as `Map<String, List<Int>>` must still parse: in a type context the parser treats
   `>>` (and `>=`, `>>=`) as a sequence of single `>` tokens. How exactly is a compiler-internal
   matter. The semantics (shift by a negative amount or by 64 or more, `&`/`|` on `Bool`) are
   defined in chapter 4.
4. Compound assignment exists for every binary arithmetic and bitwise operator (author, D1.7):
   `x op= y` means `x = x op y`, with `x` evaluated once. The exact rules (which places can be
   assigned to) are in chapter 3. `&&=` and `||=` do not exist.
5. The range operator `..` exists (author, D1.7), as in `for i in 0..n`. Whether a range is a value
   or only syntax in `for`, and whether an inclusive form (`..=`) exists, is decided in chapter 3 or
   4. `1..5` lexes as `1`, `..`, `5`, because a float needs a digit after the dot.
6. Closure syntax is decided in chapter 3. It may add tokens to this list, and it must not be
   ambiguous with the `|` operator.

## 7. Statement termination

The examples in `PLAN.md` have no semicolons **[PLAN]**. The proposed rule **[PROPOSAL]** (see D1.1):

1. The lexer emits a `Newline` token for every line end, with consecutive newlines and comment-only
   lines collapsed into one. It does not decide anything else.
2. A `Newline` **ends** a statement, a field, a variant or a section entry, **except** when it is
   ignored:
   - inside `( )` and `[ ]`;
   - after a token that cannot end an expression: a binary operator, `=`, `,`, `.`, `:`, `->`,
     `=>`, `(`, `[`, `{`;
   - before a line whose first token is `.` (method chains) **[PROPOSAL]** (see D1.2).
3. There is no `;` in v1 (D1.3). One statement per line.
4. Consequences, shown on examples:

```
let text = fs.read_text(path)?        // ends after `?`
let total = price
    + tax                             // ERROR: the statement ended after `price`
let total = price +
    tax                               // ok: the line ends with a binary operator
let names = users
    .filter(is_active)
    .map(name_of)                     // ok: next line starts with `.`
return                                // `return` with no value
    x                                 // a separate statement (unreachable code)
if ok {
    ...
}
else { ... }                          // ERROR: `else` must be on the line of `}`
```

The parser reports `+ tax` and `else` on a new line with a dedicated diagnostic and a fix hint.
Codes for these are in the parser range (chapter 9), not the lexical one.

## 8. Lexical errors

The complete list of errors the lexer reports. This is the scope of milestone M1.
**[PROPOSAL]** for the codes; the range E01xx is confirmed in chapter 9.

| Code | Error | Example |
| --- | --- | --- |
| E0101 | File is not valid UTF-8 | byte `0xFF` |
| E0102 | Unexpected character | `@`, `#`, `$`, non-breaking space |
| E0103 | Unterminated string literal | `"abc` at the end of the line |
| E0104 | Unknown escape sequence | `"\q"` |
| E0105 | Invalid Unicode escape | `"\u{D800}"`, `"\u{}"`, `"\u{110000}"` |
| E0106 | Integer literal too large | `99999999999999999999` |
| E0107 | Malformed number literal | `007`, `1_`, `0x`, `1.`, `1e`, `5i32` |
| E0108 | Float literal out of range | `1.0e999` |
| E0109 | Unescaped control character in string | a raw U+0007 inside `"..."` |
| E0110 | Carriage return without line feed | lone `CR` |
| E0111 | Non-ASCII character in identifier | `naïve` (hint: identifiers are ASCII only) |
| E0112 | Unterminated block comment | `/* a /* b */` at the end of the file |
| E0113 | Reserved literal prefix | `f"x"`, `r"x"` (hint: add a space or remove the prefix) |

Recovery: after an error the lexer emits an `Error` token covering the bad text and continues, so
that all lexical errors of a file are reported at once **[PLAN]** (section 9). The lexer never
panics on any input; fuzzing in `fuzz/` checks this **[PLAN]** (section 12).
