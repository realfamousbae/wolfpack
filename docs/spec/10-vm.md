# Chapter 10: The virtual machine

Status: **APPROVED** (author, 2026-10-22). Every **[PROPOSAL]** and **[INTERNAL]** item in this chapter is accepted.

`wolf run --vm` runs a program without Node.js, Go or Rust: `wolf` compiles it to a bytecode of
its own and runs it in a virtual machine (VM) inside `wolf` **[PLAN]** (section 10 and milestone
M13; decisions register, item 3). The VM is not a fourth target: it produces no project in `out/`
and no code to read, and it must behave exactly like the three targets (chapters 1 to 8).

Markers as in chapter 8: **[PLAN]**, **[PROPOSAL]**, **[INTERNAL]**.

## 1. Commands

1. `wolf run --vm [--example <name>] [-- <args>]` checks the project and runs it in the VM
   **[PLAN]**. `--example` and the arguments after `--` work as without `--vm` (chapter 8,
   section 2).
2. `wolf test --vm [<text>]` runs the tests in the VM and prints the same report as on the targets
   (chapter 8, section 2, rule 7). **[PROPOSAL]**
3. `--vm` and `--target` exclude each other; both together are a usage error (E0002, exit code 2).
   **[PROPOSAL]**
4. The VM needs no tools: E0801 and `wolf setup` never apply to it. It runs whatever
   `[targets] enabled` and `default` say in `wolfpack.toml` (chapter 6, section 6). **[PROPOSAL]**
5. `wolf build` had no VM form until 0.6: the bytecode lived only in memory while the program ran.
   Since 0.6 `wolf build --vm` writes it to a file (section 1b, D10.10); `wolf run --vm` still
   compiles in memory and writes no file. **[DRAFT]**
6. A project of kind `lib` cannot be run (E0002), with `--vm` as without it;
   `wolf run --vm --example <name>` and `wolf test --vm` work for it. **[PROPOSAL]**

## 1a. Seeing the bytecode (`wolf check --bytecode`)

(author, 2026-10-25, D10.9) A disassembler, for learning how the VM runs a program (D10.7).
Like `wolf check --native` (chapter 8, section 8b), it is a form of `wolf check`, since it runs
nothing and writes no file (section 1, rule 5).

1. `wolf check --bytecode` checks the project as `wolf check` does, compiles it to bytecode as
   `wolf run --vm` would, and prints on stdout the bytecode of every function of the modules of
   `src/`: `main`, the functions, the methods and the closures inside them. Modules come in the
   order of their paths, and the functions of a module in the order of its source. The functions
   of std, the tests and the examples are not printed. It works for a project of kind `lib` too.
2. `wolf check --bytecode <name>` prints only the function `<name>`: `area` and `Shape.area` are
   looked up in every module of `src/`, `shapes.area` and `shapes.Shape.area` in the module
   `shapes`, and `main` is the `main` block. When several functions have the name, all of them
   are printed. A name that names no function is E0002, without a source range.
3. Each function is a header line with its full name and its sizes, then one instruction per
   line with its index; constants, types, variants and called functions are shown by name. A
   closure follows the function that contains it, named after it: `shapes.area closure 1`,
   `closure 2` and so on in the order of the source.
   ```
   fn main.sum (params 1, captures 0, slots 5)
      0  Int(0)
      1  Store(1)
      ...
     23  Load(1)
     24  Return
   ```
4. A module that cannot run in the VM (section 3) is not compiled: in its place the output has
   one comment, `// module text.shout cannot run in the VM: it has an extern section` (or `it
   imports text.native_part`), and there is no error.
5. The diagnostics of the check go to stderr as usual, and the exit code is that of `wolf check`;
   with errors, nothing is printed on stdout.
6. **[INTERNAL]** The listing is for reading, not for tools. Its form follows the bytecode, which
   is not stable (section 4, rule 6), so it can change in any release; the tests compare it with
   snapshots.

## 1b. A bytecode file (`wolf build --vm`)

(D10.10, **[DRAFT]**) For running a program where `wolf` is installed but the project and the
tools of the targets are not: the file holds the whole program, so it can be copied and run
alone.

1. `wolf build --vm [--example <name>] [--debug]` checks the project, compiles it to bytecode as
   `wolf run --vm` would, and writes `out/vm/<package name>.wbc` (`out/vm/<example>.wbc` for an
   example). It needs no tools. A project of kind `lib`, and a module that cannot run in the VM
   (section 3, E0807), cannot be built this way.
2. `wolf run <file>.wbc [-- <args>]` runs such a file without a project: no `wolfpack.toml` is read
   and nothing is checked again. Standard input and output, files, arguments and the environment
   are those of the run; the exit code is that of the program (section 2).
3. The overrides of `[config.<module>]` (chapter 6, section 6) are those of the build: they are
   inside the file.
4. The file starts with a header naming the format and the exact version of `wolf` that wrote it.
   The bytecode is not stable (section 4, rule 6), so only the same version of `wolf` runs the file;
   any other version, or a file that is not a bytecode file or is damaged, is **E0809** and runs
   nothing. The error names both versions and says to build the file again. A future release may
   make the format stable; this one does not promise it.
5. The file is binary and is not meant to be read; `wolf check --bytecode` (section 1a) is the way
   to see the bytecode. **[INTERNAL]**: the header line is
   `wolfpack bytecode <version>` followed by the serialized image of the program.

## 2. Behaviour

The VM gives the same observable behaviour as the targets **[PLAN]**: for the same program, input
and arguments it prints the same standard output and standard error and ends with the same exit
code. In particular:

1. Exit codes (chapter 9, section 4; chapter 8, section 2, rule 3): the code of `exit`, 0 at the
   end of `main`, 1 with `error: <message>` for an `Err` from `main`, 101 for a panic.
2. Panics and assertions print the texts of chapter 7, section 3, with the source location where
   the targets print one and without it for the panics of the language (chapter 8, section 4.3),
   except in a debug build, where they too have the location of the failing operation
   (**[DRAFT]** D7.21; chapter 7, section 3, rule 1).
3. `Int` is 64 bits and overflows with a panic; division, remainder, shifts and indexing panic as on
   the targets (chapter 8, section 4.3). **[DRAFT]** (2026-10-26, D10.12): the sized integer types
   (chapter 4, section 3.1a) panic at the bounds of their width, as on the targets.
4. `Float` is printed with the canonical formatting (chapter 7, section 4.1); `Map` keeps insertion
   order (chapter 7, section 6); `String` lengths and indices count Unicode scalar values (gap G1).
5. `std.io`, `std.fs` and `std.process` behave as in chapter 7, section 7: standard input, output
   and error, files relative to the current directory, the program's arguments and environment.
   The text of `FsError.Other` comes from the system, worded as on the Rust target. **[PROPOSAL]**
   **[DRAFT]** (2026-10-26, D10.15): so do `fs.read_bytes`, `fs.write_bytes`, `io.read_bytes` and
   `io.write_bytes` (chapter 7, sections 6a and 7). The playground has no files, so there the two
   of `std.fs` fail as `read_text` does, and the bytes of `io.write_bytes` are shown as text, with
   U+FFFD for bytes that are not UTF-8.
6. `[config.<module>]` overrides of `wolfpack.toml` apply as in a build (chapter 6, section 6).
7. **Stack overflow** (D10.5). Unbounded recursion was not specified for the targets before 0.6, and
   they differed: TypeScript prints `panic: stack overflow` with exit code 101, Go printed its own
   runtime trace with exit code 2, Rust aborted. **[PROPOSAL]**: the VM limits the depth of calls
   and, past the limit, prints `panic: stack overflow` without a location and exits with 101, like
   the TypeScript target and like the other panics of the language. Go and Rust do the same since
   0.6 (chapter 8, section 4.3, D8.16 **[DRAFT]**). The limit is about calls only: the VM
   compares, copies and frees values without recursion, so deep data never reaches it (chapter 4,
   section 7.4, rule 3). **[INTERNAL]**

## 3. What the VM cannot run

1. The VM runs only wolfpack code and `std`. Code of a target cannot run in it: every module with
   an `extern` section, written or read from `native/` (chapter 7, sections 8 and 8.7), is
   **not available for the VM**. The rules of target binding (chapter 7, section 8.5) apply as if
   the VM were a target with no extern block: such a module, and every module that imports it
   directly or through others, cannot run in the VM. **[DRAFT]** The same holds for a module
   that imports a package module (chapter 7, section 8.8; proposed, D7.42): E0807 points at the
   import.
2. `wolf run --vm` and `wolf test --vm` check every module reachable from the entry module (and, for
   `wolf test`, from the tests). A module that is not available is **E0807**: the error names the
   module and points at its `extern` section (or at the import of the native module), and a note
   shows the import chain from the entry, as E0704 does. The help names the first target, the
   default one first, for which the program can be built. `wolf check` does not report it.
   **[PROPOSAL]**

   ```
   error[E0807]: module `text.shout` cannot run in the VM
    --> src/text/shout.wolf:6:1
     |
   6 | extern {
     | ^^^^^^ code of the targets is called here
     |
     = help: run it on a target: `wolf run --target ts`
     = note: imported through main -> text.shout
   ```

## 4. How it is built

These are **[INTERNAL]** choices of the implementation, listed so that the author can object.

1. **A stack bytecode of its own** (decisions register, item 3, plan default; not WebAssembly).
   A new crate `wolf_vm` compiles the IR to bytecode and runs it. Like the backends, it reads only
   the IR (chapter 8, section 1); the front end and the IR do not change for it.
2. **Instructions work on a stack of values**: constants, locals in numbered slots of a frame,
   arithmetic with overflow checks, jumps, calls and returns, building and reading structs, enum
   variants, lists and maps. Each function compiles once into a chunk of code with its own
   constants.
3. **Values carry their kind at run time**: integers, floats, booleans, strings, lists, maps,
   structs, enum variants and closures (**[DRAFT]** 2026-10-26, D10.11: and characters, a kind
   of its own holding a Rust `char`; D10.12: and the sized integers, a kind per width holding the
   Rust type of that width; D10.15: and bytes, a shared, changeable `Vec<u8>` like the vector of a
   list, whose copy and comparison need no recursion). Generic code is not specialised per type:
   one compiled function serves every type argument, and calls of interface methods are dispatched
   on the type of the value.
4. **Ownership is already checked** (chapter 5), so the VM does not check it again. A move hands the
   value over, `.copy()` makes a deep copy, and `mut` parameters refer to the place of the caller.
5. **The `intrinsic` functions of `std`** (about a hundred) are written in Rust inside the VM. The
   canonical `Float` formatting and the panic texts are checked against the same cases as the
   runtimes of the targets, so they cannot drift apart. **[DRAFT]** (2026-10-26, chapter 8,
   D8.26): `to_upper` and `to_lower` use the generated tables of the Rust runtime piece, not the
   `char` methods of the Rust that compiled `wolf`, whose Unicode version may differ (chapter 7,
   section 4.3a).
6. **The bytecode format is not stable** and is not part of the language: it can change in any
   release. A file of it (section 1b) runs only with the version of `wolf` that wrote it (E0809).
   This holds for its listing too (section 1a, rule 6; D10.9).

## 5. Tests

1. Every example and every end-to-end program of the test suite also runs in the VM, and its
   output and exit code are compared with `expected.txt`: the differential tests of `PLAN.md`,
   section 12. They need no tools, so CI runs them on every operating system. **[PROPOSAL]**
2. Exception (D10.6): the examples `fuzzy`, `textkit` and `native-slug` and the programs that
   use `extern` or `native/` cannot run in the VM (section 3). The milestone criterion of M13
   ("all examples give the same output in the VM") holds for the other examples; for these the
   tests check that `wolf run --vm` reports E0807. **[PROPOSAL]**
3. The tests of the examples (`tests` sections and `tests/`) also run with `wolf test --vm`.
4. Unit tests of `wolf_vm` and snapshots of the compiled bytecode of small functions.
