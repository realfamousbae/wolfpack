# Chapter 8: Mapping to the targets

Status: **APPROVED** (author, 2026-10-07). Every **[PROPOSAL]** and **[INTERNAL]** item in this chapter is accepted.

This chapter says how each construct of wolfpack becomes TypeScript, Go and Rust, and what the
generated projects in `out/` look like. The observable behaviour is already fixed by chapters 1–7;
this chapter must implement it exactly on every target.

Marker used here in addition to [PLAN] and [PROPOSAL]: **[INTERNAL]** marks a decision about the
internal design of a backend. By the working rules (`CLAUDE.md`) these are the drafter's to make. They
are written down so the author can see them and object.

Decisions already taken by the author for this chapter (2026-10-07):

- Go: **one package per wolfpack module**.
- TypeScript: structs and enum variants become **classes**.
- Runtime support code is **generated into each output project**, not published as packages.
- Toolchains: **Node 22+, TypeScript 5.x (strict), Go 1.24+, Rust edition 2024 (1.85+)**.
- Built-in panics carry no source location (chapter 7, section 3).

## 1. General requirements

**[PLAN]** (sections 8 and 9):

1. Backends read only the IR. Each backend first builds a tree of the target language and then
   prints it. Building text directly from the IR is forbidden.
2. Generated code passes the standard check of the target without errors: `tsc --strict`, `go vet`,
   `cargo check` (and `cargo clippy` without errors, milestone M10).
3. It is formatted the way `prettier`, `gofmt` and `rustfmt` would format it. The printers do this
   themselves; `wolf` does not call external formatters. **[INTERNAL]**
4. Doc comments of the source are carried into the output, in the doc comment style of the target
   (`/** */` in TS, `//` before the declaration in Go, `///` in Rust).
5. Output is deterministic: the same input gives byte-identical output.
6. Every generated file starts with a comment naming its source:
   `// Generated by wolf from src/users/storage.wolf. Do not edit.` Files without a source (the
   runtime, manifests) name `wolf` and its version instead. **[PROPOSAL]** for the exact text.
7. Generated code is readable. Where correctness forces a helper call (overflow checks), the helper
   has a short, obvious name.

## 2. Generated projects

| Target | Layout of `out/<target>/` |
| --- | --- |
| TS | `package.json` (`"type": "module"`), `tsconfig.json` (strict, target ES2022, module NodeNext), `src/**/*.ts`, `src/wolf_rt.ts`. Built with `tsc` into `dist/` (root `.`, so `src/` and `examples/` keep their paths), run with `node dist/src/main.js` |
| Go | `go.mod` (module path = package name, or `wolfpack.local/<name>` if Go's standard library has a package of that name, such as `cmp`; `go 1.24`), `main.go` (package `main`) for `cli`, one directory per module, `wolfrt/` package |
| Rust | `Cargo.toml` (edition 2024), `src/main.rs` or `src/lib.rs`, one file per module, `src/wolf_rt.rs` |

1. **Directory structure follows `src/`** **[PLAN]**: `src/users/storage.wolf` becomes
   `src/users/storage.ts`, `src/users/storage.rs` (with `src/users.rs` declaring `pub mod storage;`)
   and, in Go, `users/storage/storage.go` (author: a package per module; ADR 0005).
2. **Runtime** (author): each project gets a generated support module (`wolf_rt.ts`, package
   `wolfrt`, module `wolf_rt`). It holds the overflow-checked arithmetic, the insertion-ordered map,
   `Float` formatting, panic handling and the intrinsic std functions. Only the parts a program uses
   are emitted. **[INTERNAL]**
3. **Entry wrapper.** The generated `main` of each target calls the user's `main`, prints an `Err`
   as `error: <message>` to standard error with exit code 1, and turns a panic into the canonical
   message with exit code 101 (chapter 6, chapter 7). TS uses a top-level `try`/`catch` around a
   dedicated `WolfPanic` error; Go uses `recover` in a deferred function; Rust installs a panic hook
   and sets `panic = "unwind"`. **[INTERNAL]**
4. **Kind `lib`.** TS: `src/lib.ts` is the package entry (`"exports"` in `package.json`). Go: the
   root package is named after the package name without hyphens (`my-lib` gives `mylib`). Rust:
   `src/lib.rs`, crate name with `_` instead of `-`. Only the library API (chapter 6, section 4.6) is
   exported. **[PROPOSAL]**
5. **Dependencies** from `[extern.<target>.dependencies]` are copied into `package.json`
   `dependencies`, `go.mod` `require` and `Cargo.toml` `[dependencies]` **[PLAN]**. `wolf run` and
   `wolf test` fetch them: they run `npm install` in a TS project with dependencies, and Go and
   Cargo download modules and crates themselves (author, 2026-10-14).
6. **Tests** (milestone M7): TS uses `node:test` in `*.test.ts` files, Go uses `testing` in
   `*_test.go` files of the same package, Rust uses `#[cfg(test)] mod tests` **[PLAN]**.
7. **`wolf test`** (author, 2026-10-09) builds the project with its tests (tests and test helpers
   are never part of `wolf build`), runs them with the target's own framework, and prints the
   same report on every target:

   ```
   test src/main.wolf: adds two numbers ... ok
   test src/main.wolf: reports a bad token ... FAILED
   test tests/basics.wolf: counts words ... ok

   failures:

     src/main.wolf: reports a bad token
       panic at src/main.wolf:96:9: assertion failed: evaluate("1 a +") == Err(CalcError.BadToken("a"))

   test result: FAILED. 2 passed; 1 failed
   ```

   A test is named by its file and its name. Tests run in the order of the files (sorted by path)
   and of the tests in a file; a failing test does not stop the others. The failure text is the
   panic message (chapter 7, section 3). `wolf test <text>` runs only the tests whose name
   contains the text. The exit code is 0 if every test passed and 1 otherwise. In TypeScript,
   `wolf test` reads the results of `node:test` through a generated reporter; `npm test` in the
   generated project uses the default reporter of Node.js.

### 2.1 Re-exports, `tests/` and `examples/`

Added after approval, while writing the examples. **[INTERNAL]**

1. **Re-exports** of `src/lib.wolf` (chapter 6, section 2.2): TS `export { capitalize } from
   "./text/words.js"`; Rust `pub use crate::text::words::capitalize;` with the inner modules
   declared `pub(crate)`; Go has no re-exports, so the root package declares type aliases
   (`type User = model.User`) and forwarding functions.
2. **`tests/`**: TS `test/<path>.test.ts`; Go an external test package (`package mylib_test`) in the
   root directory; Rust the native `tests/<path>.rs` integration tests of Cargo.
3. **`examples/`**: TS `examples/<path>.ts` compiled as separate entry points; Go one `main` package
   per example in `examples/<path>/main.go`; Rust the native `examples/<path>.rs` of Cargo.

## 2a. The tools of the targets and `wolf setup`

`wolf run` and `wolf test` build the generated project with the tools of its target: `node`, `npm`
and `tsc` for TypeScript, `go` for Go, `cargo` for Rust (author, 2026-10-16).

1. **Where `wolf` finds a tool.** First among the tools installed by `wolf setup` in the wolfpack
   home, then on `PATH`. The wolfpack home is `~/.wolfpack` (`%USERPROFILE%\.wolfpack` on
   Windows), or the directory named by the environment variable `WOLFPACK_HOME`. A tool found
   there is run with its own environment (its directory first on `PATH`, `RUSTUP_HOME` and
   `CARGO_HOME` for Rust), so the user's own installations, `PATH` and settings are not changed.
2. **`wolf setup`** installs the tools of every target into `<home>/toolchains/`. The versions are
   fixed by the version of `wolf`; for 0.1.0 to 0.4.0 they are Node.js 24.22.0 (with npm),
   TypeScript 5.9.3, Go 1.27.2 and Rust 1.99.1 (installed with rustup 1.29.1, profile `minimal`).
   Every download comes from the official site of the tool and is checked against a SHA-256 sum
   built into `wolf`; a tool that is already installed in the right version is kept.
   - `wolf setup --target <ts|go|rust>` installs the tools of one target.
   - `wolf setup --check` installs nothing: it lists each tool, where it is found and its
     version, and exits with code 1 if a tool of an enabled target is missing.
3. **Platforms.** On Windows, Rust is the `x86_64-pc-windows-gnu` toolchain, which brings its own
   linker, so Visual Studio is not needed. On macOS, Rust needs the Command Line Tools of Xcode
   for its linker; when they are missing, `wolf setup` asks macOS to install them
   (`xcode-select --install`) and says so.
4. A download or an installation step that fails is E0804, with the tool, the URL and the reason.
   Nothing half-installed is left in `<home>/toolchains/`.
5. The release installers of `wolf` put `wolf` on `PATH` and run `wolf setup` as their last step
   (author, 2026-10-17: every way to install is listed for each system):
   - **macOS**: the terminal script `install.sh` (`curl ... | sh`), the package `.pkg`, the
     archive `wolfpack-macos-universal.tar.gz`, or Homebrew (`brew install
     realfamousbae/wolfpack/wolfpack`);
   - **Linux**: the terminal script `install.sh`, the archives `wolfpack-linux-x64.tar.gz` and
     `wolfpack-linux-arm64.tar.gz`, their static builds `...-musl.tar.gz` for systems without
     glibc 2.35 (`install.sh` picks them there), the packages `wolfpack-linux-x64.deb`,
     `...-arm64.deb`, `...-x64.rpm` and `...-arm64.rpm` (of the static builds), or Homebrew;
   - **Windows**: the terminal script `install.ps1` (`irm ... | iex`), the setup program
     `...-windows-x64-setup.exe`, the archive `wolfpack-windows-x64.zip`, Scoop (`scoop bucket add
     wolfpack https://github.com/realfamousbae/scoop-wolfpack`, `scoop install wolfpack`) or winget
     (`winget install realfamousbae.wolfpack`);
   - **every system**: building from source with `cargo install`.

   The archives contain only `wolf`: they change no `PATH` and do not run `wolf setup`; neither do
   the package managers, which say to run it. The terminal scripts check the download against the
   `SHA256SUMS.txt` of the release. (Package managers and static builds: author, 2026-10-23.)

## 2b. Updating `wolf`

Added in 0.2 (author, 2026-10-18). `wolf` can replace itself with a newer release, by a command
and after a question at start.

1. **Releases.** A release is a tag `v<x.y.z>` of the GitHub repository `realfamousbae/wolfpack`
   with the archives of section 2a, rule 5 and `SHA256SUMS.txt`. Only such releases count; a
   prerelease never does. Versions are compared as three numbers.
2. **`wolf self update`** installs the latest release, `wolf self update --version <x.y.z>` the
   given one (also an older one). It downloads the archive of the system and `SHA256SUMS.txt`,
   checks the sum, unpacks the new `wolf` next to the running one and runs `wolf --version` with
   it. Only when all of this succeeds is the old file replaced; otherwise it stays as it was. On
   Windows the running `wolf.exe` is renamed to `wolf.old.exe` first and removed by a later
   start. At the end the new `wolf` runs `wolf setup` (section 2a), which installs the tools that
   the new version fixes, if they changed. Already on the latest release, it says so and changes
   nothing.
3. **`wolf self update --check`** only asks: it prints the current and the latest version and
   exits with code 0 when they are equal, 1 when a newer release exists.
4. **Installations that `wolf` does not replace.** A `wolf` installed by a package manager is
   updated by that manager: under `~/.cargo/bin` (or `$CARGO_HOME/bin`) `wolf self update` prints
   `cargo install --locked wolfpack-lang`, under a Homebrew prefix (`/opt/homebrew`,
   `/usr/local/Cellar`, `linuxbrew`) `brew upgrade wolfpack`, under `scoop\apps\`
   `scoop update wolfpack`, under `Microsoft\WinGet\` `winget upgrade realfamousbae.wolfpack`, and
   as `/usr/bin/wolf` (a `.deb` or `.rpm` package) the package manager of the system, and it
   changes nothing. A `wolf` whose directory cannot be written is not replaced either; the error
   names the directory and the installer command.
5. **The question at start.** At most once a day `wolf` asks GitHub for the latest release in the
   background: the command that runs does not wait for the answer, and a failure is silent. The
   answer is kept in `<home>/update-check.json`. When it names a newer release, the next command
   asks first, on standard error:
   ```
   wolf 0.3.0 is available (you have 0.2.0). Update now? [y/N]
   ```
   `y` runs `wolf self update` and then the command that was asked for, with the new `wolf`. Any
   other answer runs the command as it is, and the same release is asked about again only on a
   later day.
6. **When there is no question.** Never in a pipe or a script: only when standard input and
   standard error are terminals. Never with the environment variable `CI`, never with
   `WOLFPACK_NO_UPDATE_CHECK=1`, and never when `<home>/config.toml` has `update.check = false`.
   Never for `wolf self ...`, `wolf --version`, `wolf --help`, `wolf explain` and the background
   check itself. In these cases nothing is asked and nothing is fetched.
7. A failed update is E0805, with the URL or the file and the reason. Like the other E08xx
   errors, it has no source range.

## 3. Names

| Wolfpack | TS | Go | Rust |
| --- | --- | --- | --- |
| `find_user` (function, variable, field, method) | `findUser` | `FindUser` if `pub`, else `findUser` | `find_user` |
| `FileStorage` (type, variant, interface) | `FileStorage` | `FileStorage` if `pub`, else `fileStorage` | `FileStorage` |
| `max_users` (`config` constant) | `maxUsers` | `MaxUsers` / `maxUsers` | `MAX_USERS` |
| module `users.storage` | file `users/storage.ts` | package `storage` | module `users::storage` |

1. `snake_case` to `camelCase`: each `_` followed by a letter is removed and the letter is upper-cased;
   an `_` followed by a digit is kept (`a_b_1` gives `aB_1`). With the strict `snake_case` of chapter
   1 this mapping never maps two names onto one. **[PROPOSAL]**
2. A name that is a keyword or a predeclared name of the target gets a suffix `_` in TS and Go
   (`type_`, `default_`, `len_`) and is written as a raw identifier in Rust (`r#type`).
   **[INTERNAL]**
3. Names that the backend generates (copy and equality helpers, temporaries) use prefixes that a
   wolfpack name cannot produce. If a generated helper would collide with a user name, the helper is
   renamed, never the user name. **[INTERNAL]**
4. Names made of two names can meet a user name: in TS the class of the variant `Shape.Circle`
   is `ShapeCircle`, or `Shape$Circle` when the module also declares a type `ShapeCircle`. Go has
   one namespace per package and writes private names in lower case, so even two user names can
   meet there: a private type `Chain` and a private function `chain` are both `chain`. Go gives
   names to the declarations of a module in their order, user declarations before the names made
   from them (variant types, methods written as functions), and a name that is already taken gets
   `_` suffixes until it is free (`chain_`, `shapeCircle_`). **[INTERNAL]**

## 4. Types

| Wolfpack | TS | Go | Rust |
| --- | --- | --- | --- |
| `Int` | `bigint` (ADR 0001) | `int64` | `i64` |
| `Float` | `number` | `float64` | `f64` |
| `Bool` | `boolean` | `bool` | `bool` |
| `String` | `string` | `string` | `String`; `&str` for read parameters |
| `Void` | `void` as a result, `undefined` as a value | no result; `struct{}` as data | `()` |
| `List<T>` | `T[]` | `[]T` | `Vec<T>`; `&[T]` for read parameters |
| `Map<K, V>` | `Map<K, V>` | `wolfrt.Map[K, V]` | `wolf_rt::Map<K, V>` |
| `Option<T>` | section 4.1 | section 4.1 | `Option<T>` |
| `Result<T, E>` | `{ ok: true, value: T } \| { ok: false, error: E }` | section 4.1 | `Result<T, E>` |
| function type | arrow function type | `func(...)` | `&dyn Fn(...)` as a read parameter, `Box<dyn Fn(...)>` otherwise |

### 4.1 `Option` and `Result` (ADR 0002)

1. **In function results**, where unambiguous:
   - TS: `Option<T>` is `T | undefined`, unless `T` is itself an `Option` or `Void`;
   - Go: `Option<T>` is `*T` when `T` is a struct or an enum with payloads, and `(T, bool)` otherwise
     (decisions register, item 7); `Result<T, E>` is `(T, error)` when `E` is `Error` or implements
     it (the backend generates the Go `Error() string` method from `message()`), `Result<Void, E>` is
     just `error`.
2. **As data** (fields, elements, generic arguments, nesting, and every case not covered above):
   TS `wolf_rt.Option<T>` (`{ some: true, value: T } | { some: false }`); Go `wolfrt.Option[T]` and
   `wolfrt.Result[T, E]` (small generic structs).
3. Conversions between the two forms are generated where a value moves from one position to the
   other. **[INTERNAL]**
4. Function **values** (closures, functions stored in variables or passed as arguments) return an
   `Option` (and in Go a `Result`) in the data form in TS and Go, because what they return is
   usually stored (`list.map`). A declared function used as a value is wrapped so that it returns
   the data form. (Author, 2026-10-09, ADR 0008; Go: 2026-10-13, ADR 0009.)

### 4.2 `Int` in TypeScript (G10)

1. All `Int` values are `bigint`. Arithmetic goes through `wolf_rt` helpers that check the 64-bit
   range (`add(a, b)`, `mul(a, b)`), because `bigint` never overflows.
2. Where JS needs a `number` (array indices, `.length`, string positions), the backend converts
   explicitly: `items[Number(i)]` after a range check, `BigInt(items.length)`. **[INTERNAL]**
3. `print` and `to_string` of an `Int` never show the `n` suffix (ADR 0001).

### 4.3 Overflow and other built-in panics

| | TS | Go | Rust |
| --- | --- | --- | --- |
| `+ - *` | `wolf_rt` helpers | `wolfrt.Add(a, b)` etc. (Go wraps silently) | native operators with `overflow-checks = true` in every Cargo profile |
| `/ %` | helpers (zero, `MIN / -1`) | helpers (`MIN / -1` wraps in Go) | native (panics already) |
| shifts | helpers | helpers | helpers (Rust masks the amount) |
| index | helper with range check | helper with range check (ADR 0009) | helper with range check (`items.at(i)`; author, 2026-10-13) |

The panic hook (Rust) and `recover` (Go) translate the target's own panic message into the canonical
message of chapter 7, for example Rust's `attempt to add with overflow` becomes
`panic: integer overflow`. **[INTERNAL]**

## 5. Declarations

### 5.1 Structs

- **TS** (author, ADR 0005): a `class` with the fields as public properties, a constructor taking one
  object with all fields (`new User({ id: 1n, name: "Ann" })`), inherent methods as methods,
  associated functions as `static` methods, interface implementations as `implements`.
- **Go**: a `struct`; methods with a pointer receiver if any method of the type takes `mut self`,
  else a value receiver. Read parameters of struct type are passed by value, `mut` parameters by
  pointer **[PLAN]**.
- **Rust**: a `struct`; recursive fields are wrapped in `Box` **[PLAN]**.

### 5.2 Enums

| Kind | TS | Go | Rust |
| --- | --- | --- | --- |
| no payloads | union of string literals: `"Red" \| "Green"` | `type Color int` with `const` values | `enum` with `#[derive(Clone, Copy, ...)]` |
| with payloads | one class per variant with a `kind` field, and a union type `Shape = ShapeCircle \| ShapeRect` | a sealed interface with an unexported marker method and a struct per variant **[PLAN]** | `enum` |

Positional payloads are named `_0`, `_1` in TS, `F0`, `F1` in Go. Methods of an enum with payloads
are generated once as a function and called from each variant class (TS) or from the interface
method (Go). **[INTERNAL]**

### 5.3 Interfaces

| | TS | Go | Rust |
| --- | --- | --- | --- |
| interface | `interface` | `interface` | `trait` |
| as a bound | generic constraint; a dictionary parameter for `Display` and `Comparable` (5.4) | dictionary parameter (5.4) | trait bound |
| as a value type | the interface type | the interface type | `Box<dyn Trait>` |

`.copy()` on an interface value (author, 13b) calls a hidden copy method that every implementation
gets (`Box<dyn Trait>` gets a `Clone` impl through it). **[INTERNAL]**

### 5.4 Generics

1. TS and Rust use their own generics. Bounds map in Rust to traits: `Equatable` to `PartialEq`,
   `Copyable` to `Clone`, `Hashable` to `Hash + Eq`, `Comparable` to a runtime trait implemented for
   `i64` and `String`.
2. **Go** (register item 14): a single Go constraint cannot be satisfied both by `int64` and by a
   struct with a method. The Go backend therefore uses **dictionary passing**: every bound of a type
   parameter becomes an extra parameter holding the needed operations
   (`func Max[T any](ord wolfrt.Ord[T], a T, b T) T`), and each call site passes the right one.
   **[INTERNAL]** This keeps one generated function per generic function and works for every type.
3. **TS** also passes dictionaries, for the bounds `Display` and `Comparable` only: a payload-less
   enum is a string at run time, so only the call site knows which `to_string` and `compare` to
   use. **[INTERNAL]**
4. Generic inherent methods (chapter 4) are emitted in Go as free generic functions
   (`StackMap[T, U](s Stack[T], f func(T) U) Stack[U]`). When Go generic methods become available
   (Go accepted them in 2026), the backend may switch. **[INTERNAL]**

### 5.5 Equality and copies

`==` and `.copy()` (chapter 4, section 9) map to `===` / native `==` / `PartialEq` and to nothing for
copy types. For other types TS uses the structural `eq` and `copy` of the generated runtime (author, 2026-10-09,
ADR 0008), Go generates `equals` and `copy` functions, and Rust derives `PartialEq` and `Clone`.
**[PLAN]**

**Depth** (chapter 4, section 7.4, rule 3). The TypeScript `eq` and `copy` keep a list of the
parts still to visit instead of calling themselves, so the depth of a value does not matter. Go's
generated `equals` and `copy` and Rust's derived `PartialEq`, `Clone` and drop call themselves once
per level, so the runtimes make the stack deep enough: the Go entry wrappers and the test wrapper
let a goroutine's stack grow to 2 GiB (`debug.SetMaxStack`; Go's own limit is 1 GB), and the Rust
ones run the program or the test on a thread with a stack of 2 GiB (512 MiB when the system refuses
2 GiB, the current thread when it refuses both). Only the part of a stack that the program reaches
takes memory, so a program whose own recursion never ends uses up to that much before it stops.
The generated code itself does not change. **[INTERNAL]**

## 6. Ownership

**[PLAN]** (section 4):

| Mode | TS | Go | Rust |
| --- | --- | --- | --- |
| read | the reference | value (structs), the slice/map header | `&T`, `&str`, `&[T]` |
| `mut` | the reference | `*T` | `&mut T` |
| `own` | the reference | value | `T` |
| `.copy()` | generated copy | generated copy | `.clone()` |
| move | nothing | nothing | move |

Because the ownership check guarantees no observable aliasing (chapter 5, section 9), TS and Go never
copy defensively.

## 7. Statements and expressions

1. `if` and `match` used as expressions become statements assigning a temporary in TS and Go (both
   lack expression `if` and `switch`). A simple `if`/`else` of two plain values becomes a TS ternary.
   **[INTERNAL]**
2. `match` becomes an `if`/`else if` chain on `kind` in TS (a labeled block when an arm has a
   guard), because a `switch` would catch the `break` of a surrounding loop and cannot express
   nested patterns (author, 2026-10-09, ADR 0008); a type `switch` (or a
   value `switch` for payload-less enums) in Go, and `match` in Rust **[PLAN]**.
3. `?` becomes an early `return` in TS, `if err != nil { return ..., err }` in Go and `?` in Rust
   **[PLAN]**. Coercion to `Error` (chapter 4) is emitted explicitly where needed.
4. Closures become arrow functions, function literals and `move` closures.
5. `for x in xs` becomes `for (const x of xs)`, `for _, x := range xs`, `for x in &xs` (or
   `iter_mut`, `into_iter` for `mut` and `own`).
6. String length, positions and slices use scalar-value helpers in TS and Go; Rust uses `chars()`
   (G1). String comparison uses a helper in TS only (chapter 4).

## 8. `extern`

1. Imports are generated from the path strings of chapter 7: `import { parse } from "some-lib"`,
   `import "crypto/sha256"`, `use sha2::Sha256;`.
2. Boundary conversions (author, 2026-10-14):
   - TS: `Int` is passed to extern code as a `number` and checked to be a safe integer (otherwise a
     panic); returned numbers must be integers and become `bigint`. Exceptions become `Err` or a
     panic (chapter 7).
   - Go: values are passed with the Go types of section 4, and `Int` parameters are `int64`. An
     `Int` result may be of any Go integer type (`int`, `uint32`, ...) and is converted with a
     check. Otherwise the Go function must have exactly these parameter and result types, and
     `go build` reports a mismatch.
   - Rust: read `String` and `List` parameters are passed as `&str` and `&[T]`; `Int` parameters
     and results may be of any Rust integer type (`usize`, `u32`, ...) and are converted with a
     check; `Result` errors are converted with their `Display` text.
   - A checked conversion that fails is a panic: `integer too large for extern code` for a
     parameter, `integer overflow` for a result, on every target.
   - `Map<K, V>` (0.2; chapter 7, section 8.4, rule 6) is never passed as the map of the runtime,
     whose contents are internal. Keys and values inside it are converted by the rules above:

     | | TS | Go | Rust |
     | --- | --- | --- | --- |
     | parameter | a new `Map<K, V>` | a new `map[K]V` | `&HashMap<K, V>` of `std::collections`, built for the call |
     | result | a `Map`, or for `String` keys a plain object (its own enumerable properties) | `map[K]V`; `Int` keys and values of any Go integer type | any `IntoIterator<Item = (K, V)>`: `HashMap`, `BTreeMap`, a `Vec` of pairs; `Int` of any Rust integer type |

     The parameter is built in the insertion order of the wolfpack map where the target type has
     an order (TS). The result is sorted by key when it is converted.
   - A callback (0.2; chapter 7, section 8.4, rule 7) is passed as a function of the target that
     converts its arguments from the target and its result to it, then calls the wolfpack
     function value:

     | TS | Go | Rust |
     | --- | --- | --- |
     | an arrow function, `(a: number) => string` for `fn(Int) -> String` | a function literal of exactly the declared Go types, `func(a int64) string` | a reference to a closure, `&\|a: i64\| -> String { ... }`, which fits parameters of type `impl Fn(..)`, `F: Fn(..)` and `&dyn Fn(..)` |

     In Go and Rust the integer types of a callback are exactly `int64` and `i64`: a function
     literal or a closure has one type. A read `String` parameter of a callback is `&str` in
     Rust, a read `List` parameter `&[T]`. In TS a wrapper that turns exceptions of the extern
     code into `Err` lets a panic of the callback through.
   - A record (0.2; chapter 7, section 8.4a) is built field by field, each field converted by the
     rules above:

     | | TS | Go | Rust |
     | --- | --- | --- | --- |
     | parameter | a plain object `{ maxSize: 3 }` | a value of the struct type, `geo.Point{X: 1.5, Y: 2}` | a value of the struct type, `geo::Point { x: 1.5, y: 2.0 }`; a read parameter by reference |
     | result | any object with these properties | a value of the struct type | a value of the struct type |
     | `Int` fields | `number`, checked | exactly `int64` | any Rust integer type, checked |

     Go pointers to records (`*geo.Point`) are not part of 0.2 as parameters and record fields;
     an `Option` of a record is a pointer, as below.
   - An `Option<T>` **parameter** (0.2, author, 2026-10-21, D8.12) is passed in the form the target
     uses for "a value or nothing", with the value converted by the rules above; `None` is
     `undefined`, `nil` or `None`:

     | `Option<T>` parameter | TS | Go | Rust |
     | --- | --- | --- | --- |
     | form | `T \| undefined` | `*T`, a pointer to a copy | `Option<&T>` of the read form of `T` |
     | `Option<Int>` | `number \| undefined`, checked | `*int64` | `Option<i64>` |
     | `Option<String>` | `string \| undefined` | `*string` | `Option<&str>` |
     | `Option<List<T>>` | `T[] \| undefined` | `*[]T` | `Option<&[T]>` |
     | `Option<Point>`, a record | a plain object or `undefined` | `*geo.Point` | `Option<&geo::Point>` |

     `Float` and `Bool` are passed by value in Rust (`Option<f64>`, `Option<bool>`), like `Int`;
     a `Map` as `Option<&HashMap<K, V>>`; an opaque type `X` as `*X` in Go and `Option<&X>` in
     Rust. `T` may not itself be an `Option` (E0702), since `T | undefined` cannot tell the two
     `None`s apart. Results keep the forms of section 4.1.
3. Opaque types are used as they are: the target type in TS and Rust, the declared type in Go.

## 8a. Code of the project (`native/`)

Added in 0.2 (author, 2026-10-18). `wolf build` copies the files of `native/<target>/` byte for
byte into the generated project of that target, and the generated code imports them:

| Target | Copied to | A call of `"native:slug#slugify"` / `"native:slug.Slugify"` / `"native:slug::slugify"` |
| --- | --- | --- |
| TS | `out/ts/src/native/` | `import { slugify } from "./native/slug.js"`, relative to the module |
| Go | `out/go/native/` (packages of the generated module) | `import "<module>/native/slug"`, then `slug.Slugify(...)` |
| Rust | `out/rust/src/native/`, with a generated `src/native/mod.rs` declaring the modules | `crate::native::slug::slugify(...)` |

The conversions at the boundary are those of section 8. The files are copied only for the target
being built; the playground has no native code. A function of a native module (chapter 6, section
1a) is generated exactly like an extern function with the `native:` path of chapter 7, section 8.7,
rule 6, and a record of a native module like a struct bound with `struct Name from` (chapter 7,
section 8.4a), with two differences (author, 2026-10-21, D7.18): each field has the type the reader
found, so an `Int` field may be of any integer type, converted with a check, and a `Float` field
`float32` or `f32`, converted as for parameters and results; and a Go field keeps its Go name (the
Go field `ID` is the wolfpack field `id`).

## 8b. Seeing what the compiler read (`wolf check --native`)

Added in 0.2 (author, 2026-10-21, D8.13).

1. `wolf check --native` checks the project as `wolf check` does, and also prints, for each native
   module the project imports, what the compiler read from each target (chapter 7, section 8.7):
   `wolf check --native native.text.slug` prints one native module of the project, imported or not.
2. The output is wolfpack source on stdout, one module after the other, in the order of their
   paths: a comment that names the files read, an `extern` block with one target block per target
   that has code, written as the declarations of chapter 7, sections 8.1 to 8.4a with their
   `native:` paths, and a `types` section with the records. Each item that is not available is a
   comment `// not available: <name>: <reason>` in its target block; methods and associated
   functions (chapter 7, section 8.7, rule 17), which written `extern` blocks cannot declare, are
   comments `// method of Index: fn add(self, word: String) -> Void`. The output can be pasted into
   a module as a written `extern` block, to rename or change what the reader chose.
3. The diagnostics of the check go to stderr as usual, and the exit code is that of `wolf check`.
   A module path that names no native module of the project is E0716, without a source range.

## 9. Diagnostics

Added in M6 (author, 2026-10-09). Like driver errors, these have no source range.

| Code | Error |
| --- | --- |
| E0801 | A tool of the target is not installed (`node`, `tsc`, `go`, `cargo`); the hint names `wolf setup` |
| E0804 | `wolf setup` could not download or install a tool (section 2a); the tool, the URL and the reason are shown (author, 2026-10-16) |
| E0802 | A tool of the target rejected the generated code. This is always a compiler bug: the output of the tool is shown with a request to report it |
| E0803 | The packages of `[extern.<target>.dependencies]` could not be fetched (`npm install` failed); the output of the tool is shown (author, 2026-10-16) |
| E0805 | `wolf self update` could not download, check or install a release (section 2b); the URL or the file and the reason are shown (0.2) |
| E0806 | A tool of the target rejected a project that has code in `native/<target>/` (section 8a); the output of the tool is shown. The error is usually in a native file or in an `extern` declaration that does not match it, so unlike E0802 it is reported for every rejection of such a project (author, 2026-10-19) (0.2) |
